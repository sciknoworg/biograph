# KISSKI chat-ai endpoint: model behaviour under long structured-output load

**From:** Jennifer D'Souza, TIB — biograph project
**Endpoint:** `https://chat-ai.academiccloud.de/v1`
**Date:** 2026-10-01
**Probe script:** `scripts/kisski_model_probe.py` (reproducible, generates its own prompts)

---

## What we are asking

We extract knowledge graphs from scientific biographies. One extraction is a single chat
completion that must return **tens of thousands of tokens of schema-valid JSON**. Several
models on this endpoint fail at that, and they fail in different ways, so we wrote a probe to
separate the causes before raising anything with you.

**Most of the endpoint is healthy: 11 of 14 models completed our load probe correctly.** Four
observations below look like they need your input; the rest we can fix on our side, and we say
which is which.

---

## Method

Each model gets two streamed calls at `temperature=0`:

| probe | input | `max_tokens` | asks |
|---|---|---|---|
| **smoke** | one sentence | 768 | does the model respond at all, and how fast does it start? |
| **load** | ~25,000 tokens of generated filler | 16,000 | can it sustain long, strictly structured output? |

The load probe asks for a JSON object containing an array of exactly 400 objects, each with
four named keys, taken from a record list in the prompt. The returned JSON is parsed and checked
against that shape, so `ok`, `unparseable`, `empty` and `3 of 400 records` are distinguished.

**All prompts are generated by the script.** Nothing from our corpus is involved, so you can
re-run it and get comparable numbers. Time to first token (TTFT) is measured by streaming and
reported separately from total time, and reasoning tokens are counted apart from content.

## Observations we would like your input on

### 1. `glm-5.3-flash` is far slower on a small request than on a large one

| request | input | `max_tokens` | total |
|---|---|---|---|
| smoke | one sentence | 768 | **903.4s** |
| load | ~25,000 tokens | 16,000 | **145.8s** |

A one-sentence prompt takes **six times longer** than one 400× larger. This reproduced across
two separate sweeps on different days. In an earlier sweep with `max_tokens=64` the same smoke
prompt returned in **0.6s**, so the behaviour appears between 64 and 768 output tokens on small
inputs. The model is otherwise healthy — its load result is correct and fast.

Is there routing, batching or a warm-up path that treats small requests differently?

### 2. `meta-llama-3.1-8b-instruct` returns `finish_reason: tool_calls` with no content

No tools were offered in the request — the call contains only `messages`, `temperature`,
`max_tokens` and `stream`. The model nevertheless terminated with `tool_calls` and streamed
zero content characters, after 73.5s. The smoke probe on the same model answers normally in
0.3s.

Is tool-calling being injected server-side for this model, or is it a template/config issue?

### 3. Reasoning tokens count against `max_tokens`, and the result is indistinguishable from silence

Four models finished with `length`. Two returned **no content at all** while producing
substantial reasoning:

- `qwen3.8-27b` — 0 content characters, **28,781 reasoning characters**
- `qwen3.5-397b-a17b` — 18,821 content characters after **17,034 reasoning characters**, and
  **133.8s before the first content token**

From a client's perspective this is a `200` with an empty `content` stream, which is
indistinguishable from a model that had nothing to say. We can raise `max_tokens` on our side —
and will — but two questions would help:

- Which models on this endpoint emit reasoning before content?
- Is the reasoning counted against `max_tokens`, and is there a documented way to budget for it
  separately?

### 4. `devstral-2-123b-instruct-2512` sustains 1.9 tokens/second

It completed correctly, but took **3,470 seconds** for output that `openai-gpt-oss-120b`
produced in 90s — roughly 40× slower for a comparable result. Is that expected for this model
on this hardware, or a sign of contention?

---

## Not a defect, recorded for completeness

`apertus-70b-instruct-2509` returns:

> This model's maximum context length is **20080 tokens**. However, you requested 16000 output
> tokens and your prompt contains at least 4081 input tokens, for a total of at least 20081
> tokens.

So its context is ~20k total, input and output combined. Our real workload needs ~22k input
before any output, so this model cannot serve it at any setting. Noted only so the published
context figure is easy to find — one aside: the message reports "at least 4081 input tokens"
where the probe sent ~25,000, which may just be the server stopping its count once the request
is known to be over budget.

---

## What we are fixing on our side

Two models that fail in our production pipeline **pass this probe cleanly** —
`mistral-medium-3.5-128b` and `gemma-4-31b-it` both returned correctly shaped output. Those
failures are therefore ours, in prompt or token budgeting, not yours. We mention it so the
list above is not read as a longer complaint than it is.

## Reproducing

```bash
export BIOGRAPH_API_KEY=...            # the key is read from the environment, never argv
python scripts/kisski_model_probe.py --base-url https://chat-ai.academiccloud.de/v1 --out report.md
python scripts/kisski_model_probe.py --base-url ... --skip-load        # availability only
python scripts/kisski_model_probe.py --base-url ... --models glm-5.3-flash
```

Defaults: `--input-tokens 20000`, `--records 400`, `--max-tokens 16000`, `--smoke-tokens 768`,
`--timeout 900`. Happy to share the script directly or run any variation that would help.
